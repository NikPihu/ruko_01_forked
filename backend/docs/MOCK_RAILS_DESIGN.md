# Plan: getting payee and number details from just a UPI ID and a phone number

## Context
- **What the app sees:** at the moment of payment, a UPI app knows only the **payee's UPI ID** (for example `ravi.k@okaxis` or `98xxxxxx10@ybl`) and, from the phone, the **number calling the user**.
- **What Jagdeep wants to know:**
  - How do real NPCI, bank and government systems turn those two strings into risk details (who owns the account, its age, whether it's a mule, whether the number is reported)?
  - How do we build a mock that is accessed **the same way**?
- **Approach:** this is an experimental repo. The PDF is guidance, not a strict contract, so the mock is designed to look like the real world: **one mock service per real organisation**, each reached only through the identifier it would really accept.

---

## 1. How it works in reality: identifier → key → details

Every system indexes its data by an identifier. The UPI ID or phone number either **is** that key or **resolves** to it.

```
UPI ID "ravi.k@okaxis"
  │  handle "@okaxis" ──▶ NPCI routing table: which PSP/bank issued this handle
  ▼
NPCI asks that PSP/bank to resolve it ──▶ the actual bank account (stays inside the bank)
  ├─ Validate-address reply (any UPI app gets it): registered name, person/merchant, MCC, verified flag
  ├─ Payee's bank only: account open date, KYC age, inflow/outflow, how fast money leaves, MuleHunter score
  └─ Shared lists (banks/PSPs subscribe): I4C Suspect Registry keyed by UPI ID / account / phone

Phone number "+91 98xxxxxx10"
  ├─ DoT FRI: keyed by mobile number → MEDIUM / HIGH / VERY_HIGH
  ├─ I4C Suspect Registry: numbers are listed too
  └─ NPCI number mapper: number → its default UPI ID (number-based IDs like 98…@ybl)
```

**Who can see what** (the real access boundaries):

| Detail | Looked up by | Who really has it |
|---|---|---|
| Registered name, person or merchant, MCC | UPI ID | **Any UPI app**, through NPCI validate-address |
| Account age, KYC age, money in and out, forwarding speed | Account behind the UPI ID | **Only the payee's bank** |
| Unique payers recently (fan-in) | UPI ID / account | The payee's bank (or its app); network-wide only through RBI's DPIP |
| MuleHunter score | Account | Inside each bank that runs it |
| Suspect Registry hit | UPI ID, account, phone | Banks and PSPs that subscribe |
| FRI level | Mobile number | Banks and PSPs integrated with DoT |

**Two numbers, two uses:**
1. **The caller's number**, from the phone's call state: FRI and the registry. This is the scammer's line.
2. **The payee's number**, when the UPI ID is number-based: also FRI and the registry.

## 2. Mock design: one service per real organisation

Each mock only accepts the identifier the real one would accept, and only answers what the real one would show. This makes RUKO's code look like a real integration, and makes "what can RUKO see?" honest.

```
                      ┌───────────────────────────── mock world ─────────────────────────────┐
RUKO risk engine ───▶ │ mock NPCI      resolve(upi_id) → handle→bank, name, type, MCC          │
 (has: upi_id,        │                number_to_vpa(mobile)                                  │
  caller number)      │       │ routes by handle                                              │
                      │       ▼                                                               │
                 ───▶ │ mock banks     payee_risk(upi_id) → account age, KYC age, fan-in,     │
                      │ (okaxis, ybl,…) pass-through, hold time, MuleHunter score             │
                      │                 only "partner" banks answer; others = unknown          │
                 ───▶ │ mock DoT FRI   fri(mobile) → NONE/MEDIUM/HIGH/VERY_HIGH               │
                 ───▶ │ mock I4C       registry(upi_id | mobile) → listed, reported_on         │
                      └───────────────── shared: accounts, ledger, sim clock ──────────────────┘
```

**Shared data underneath** (generated by the simulator):
- `accounts`: upi_id, mobile, bank, handle, holder name, person or merchant, MCC, verified, created_at, KYC date, region, is_mule, mule type
- `ledger`: ts, from_upi, to_upi, amount
- `reports`: the scam victim reports that feed FRI and the registry
- a **sim clock**, so demos are repeatable and you can "jump 3 days"

**Each mock's rules (reproducing real blind spots):**
- **Mock NPCI**
  - Parse the handle after `@` and look it up in the handle→bank table.
  - Return only the public fields: name, type, MCC, verified.
  - An unknown handle means invalid.
- **Mock banks**
  - Compute payee features from the ledger: unique payers in 6 h and 7 d, pass-through ratio, median hold time, repeat-payer ratio.
  - Add account age and KYC age, plus a MuleHunter score refreshed **once per simulated day**.
  - **Only partner banks answer.** A non-partner returns unknown, the same as reality without DPIP.
  - A visibility switch (none / own bank / all banks via DPIP) shows how RUKO performs as data access grows.
- **Mock DoT FRI**
  - Rate each number from **reports with a 1–7 day lag**: weight × recency, bucketed into levels.
  - Fresh SIMs and VoIP callers stay NONE.
- **Mock I4C registry**
  - An identifier is listed only after a report plus its lag. About 50% of victims report.
  - About 1% false entries, to test the "mass false reports against an honest payee" case.

**The RUKO side (the risk engine):**
- On Pay, the engine calls NPCI, the payee's bank, FRI and the registry **in parallel**, with a total timeout of about 150 ms and a short cache.
- Anything slow or failed counts as **unknown, never safe**. If the whole decision exceeds 200 ms, the payment proceeds.
- Bank, FRI and registry answers are all the **payee/intel family**, so they don't count as separate corroboration.
- **Privacy option:** RUKO can hash UPI IDs and numbers (SHA-256 plus salt) before storing or logging them. The mocks can index by the same hash, which mirrors how banks share hashed identifiers.

---

## 3. Build order (when coding starts)
1. Simulator data: accounts and handles, ledger, mules, reports with lag.
2. Mock NPCI: resolve the UPI ID and the number-to-VPA mapping.
3. Mock bank: payee features from the ledger, the partner-only rule, daily MuleHunter.
4. Mock FRI and registry, built from reports with lag and false entries.
5. RUKO intel adapter: parallel calls, timeout, cache, unknown on failure.
6. The mule pump script: many small payments in, quick forwarding out, so the bank features light up live.

## Verification
1. Resolve `ravi.k@okaxis` and get only the public fields. Asking NPCI for account age is not possible.
2. A fresh mule at a partner bank shows high fan-in and pass-through but a `null` MuleHunter score (refresh not yet run), and is **not** in the registry. RUKO still flags it from bank features plus call context.
3. The same mule at a non-partner bank shows unknown bank features; RUKO relies on call context and behaviour.
4. Jump 3 days after a victim report: the registry lists the payee and the caller's number becomes HIGH or VERY_HIGH in FRI.
5. A kirana shop (high fan-in, high repeat-payer ratio, slow outflow) is not flagged.
6. With a slow mock (added delay), RUKO answers within 200 ms and treats the intel as unknown.
